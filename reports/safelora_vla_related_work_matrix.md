# SafeLoRA-VLA Related Work Matrix

Date: 2026-07-08

This matrix is literature and source alignment only. It is not a method claim.

| Work | What it solves | What it does not solve | SafeLoRA difference if continued | SOTA axis relevance |
| --- | --- | --- | --- | --- |
| SafeManip | Defines reusable LTLf temporal safety templates, predicate grounding, DFA monitoring, and safe-success style analysis for RoboCasa365 rollouts. | It is an evaluation benchmark. It does not train, fine-tune, adapt, or intervene in a VLA policy. Official reproduction needs heavy RoboCasa365 policy assets and GPU rollout generation. | SafeLoRA would use SafeManip-style property violations as training signals for LoRA/adapter updates, then evaluate safe-success and property violation changes. | Strongest fit for temporal violation rate, safe success, unsafe success, property-wise violation rate, and unsafe exposure. |
| LIBERO-Safety | Provides official LIBERO-derived safety suites, 5 task families, 3 difficulty tiers, public code, public LeRobot-format dataset, assets, and a pi0.5 model release. | The released training corpus is safe/collision-free demonstrations; the paper notes the lack of dense unsafe-event annotation. The public code does not expose a small official training smoke or property-conditioned LoRA recipe. | Candidate official source for a later SmolVLA adapter smoke, but SafeLoRA needs explicit unsafe/property labels or rollout-derived violations before preference training is meaningful. | Useful for success/safety tradeoff, physical safety, semantic safety, and robustness; weaker for SafeManip-style temporal property labels. |
| ForesightSafety-VLA | Defines a 13-category taxonomy across Safe-Core, Safe-Lang, and Safe-Vis, with cumulative safety cost, risk exposure time, and four-quadrant outcomes. | As of this gate, no official code/data/source path was found beyond the arXiv paper. No runnable small subset or LoRA route is inspectable. | If source appears, it would be a strong benchmark for process-level risk losses and RET/CC metrics. | Strong fit for cumulative safety cost and risk exposure time, but source availability is currently blocked. |
| SafeVLA-Bench | Adds post-hoc STL safety scoring to native LIBERO and RoboCasa rollouts, reporting SR, safety, successful-but-unsafe rollouts, and violation severity. | It is a benchmark layer, not a policy adaptation method. This run did not find an official code/data package. | Could become a useful evaluation axis if code becomes available; SafeLoRA would need to improve SBU/VSI without lowering native SR. | Strong for unsafe-success and severity metrics, conditional on source access. |
| SafeVLA | Proposes integrated safety alignment through constrained learning and Safety-CHORES, reporting safety improvement and success retention against FLaRe. | It is a heavy safe-RL/constrained-learning route in AI2-THOR/ProcTHOR-style assets, not a low-compute LoRA route. It needs Docker/GPU/assets/checkpoints. | SafeLoRA would be lighter and property-conditioned, but must avoid becoming a weaker safe-RL reward-penalty variant. | Relevant as a safety-aligned training baseline and method-gap pressure, not as the selected local benchmark. |
| PACS and safety filtering | Path-consistent safety filtering modifies execution through reachability or similar safety checks while trying to stay on the intended action path. | It does not change the VLA policy weights and may reduce violations through runtime intervention rather than learned safe behavior. | SafeLoRA must show weight-level safety improvement and beat PACS/stop/filter baselines on utility-retained safe success. | Critical anti-filtering baseline for safe-success and no-op/slowdown behavior. |
| VLSA and CBF-style filters | Add plug-and-play safety constraint layers that minimally adjust nominal VLA actions for collision avoidance or geometric safety. | Usually depend on geometric state/perception and enforce local constraints rather than learning temporal property-conditioned behavior. | SafeLoRA would adapt policy behavior; filters remain required deployment-time baselines. | Strong collision/contact baseline, weaker for sequencing, containment, contamination, and release timing. |
| OpenVLA / OpenVLA-OFT | OpenVLA supports LoRA/full fine-tuning; OpenVLA-OFT improves LIBERO success through continuous actions, action chunking, parallel decoding, and L1 regression. | OpenVLA-OFT reported training uses multi-A100/H100-class resources; it optimizes success/speed, not safety-specific temporal properties. | SafeLoRA could borrow LoRA/adaptation mechanics but must not run heavy OpenVLA-OFT locally. | Required success baseline/context; not a local execution target in this gate. |
| SmolVLA | A 450M VLA intended for affordable robotics, LeRobot datasets, continuous actions, and consumer-hardware deployment. | Official docs recommend ordinary fine-tuning and do not provide property-conditioned safety LoRA for LIBERO-Safety. Full useful fine-tuning still takes substantial GPU time. | Best low-compute candidate model if an official safety dataset path and property labels become usable. | Candidate model for bounded adapter smoke, not enough by itself for safety SOTA. |
| Generic DPO / ORPO | Provide lightweight preference optimization objectives using chosen/rejected pairs, with DPO avoiding explicit reward modeling and ORPO combining preference penalty with SFT. | They are generic preference objectives; monitor-derived safe-over-unsafe pairs alone are not novel. | SafeLoRA must beat generic DPO/ORPO LoRA on the same official pair set and show property-wise improvements. | Mandatory preference-tuning baseline and highest novelty threat. |
| Safety-only / stop-on-risk / no-op | Can reduce violations by stopping, aborting, clipping, or refusing risky actions. | These approaches often collapse task utility and can create fail-safe but unsuccessful rollouts. | SafeLoRA must improve safe-success and task retention, not only safety rate. | Mandatory baseline for utility retention, no-op rate, and safe-success. |

## Alignment Verdict

SafeLoRA has a method-level opening only if it produces policy-weight adaptation
that improves official safety metrics while preserving utility. The closest
existing benchmarks diagnose the gap; generic preference tuning and safety
filters are the strongest threats to novelty.
